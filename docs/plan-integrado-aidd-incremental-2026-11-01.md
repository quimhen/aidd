# Plan integrado AIDD: cambios y auditorías incrementales

Estado: plan de implementación autorizado por el usuario; no es evidencia de cierre. Alcance: AIDD primero; después volver a b1SycLink. El trabajo existente en el árbol se conserva y se revisa antes de integrarlo.

Decisión posterior del usuario: «hooks de codex los podemos bypasear, lo demas si debemos terminar». Los hooks de Codex no son requisito para avanzar ni para concluir los demás componentes. Usar una ruta alternativa que registre la aprobación y la auditoría que realmente ocurrieron; no fabricar eventos de hooks ni atribuirles una acción que no observaron. La auditoría incremental debe seguir limitada a lo nuevo o afectado.

Límite práctico de confianza: la ejecución local de AIDD y su proceso auditor independiente constituyen la fuente de evidencia del proyecto. Para filas declaradas explícitamente herméticas, la lista de entradas y variables es un contrato del responsable de la spec, no una afirmación de aislamiento de sistema; el reuso comprueba ese contrato, la evidencia y el entorno declarado. BD, red y otros estados externos no se reutilizan sin identificar su estado. No se requieren hooks de Codex para estos flujos.

## Contrato único de unidad

1. Una spec mantiene una línea base y una secuencia de enmiendas con ID y versión estables. Cada unidad declara sus archivos de tareas, objetivos de código, entradas de pruebas, referencias visuales y unidades padre. Los manifests y relaciones se validan antes de usar sus resultados: duplicados, ciclos, archivos ausentes o rutas ambiguas no producen un sello válido. Las specs existentes sin unidades siguen usando el flujo anterior.
2. Para cada unidad se calcula una huella de sus tareas y requisitos, bytes de objetivos y entradas, configuración relevante y huellas transitivas de dependencias. Las referencias visuales incluyen archivo de referencia, estado, rol y viewport; no se confunde la huella de una imagen con una comparación visual ejecutada. Los resultados históricos se conservan inmutables y cada resultado declara exactamente la huella y versión del algoritmo evaluadas.
3. `impacto` compara las huellas y presenta, sin ejecutar nada, la causa por unidad: contenido propio, dependencia compartida, regla/runner, evidencia o entorno. La modificación de un archivo fuera de la clausura no invalida la unidad. Si una dependencia compartida cambia, solo se invalidan sus consumidores y descendientes. Si no puede conocerse el alcance, se informa como indeterminado y se verifica la parte no demostrada; no se marca PASS ni se vuelve a auditar por defecto toda la spec.

## Pruebas y auditorías

4. Cada comprobación registra comando, resultados, casos cubiertos, entradas, salidas, intérprete y condiciones externas relevantes. Una comprobación idéntica y válida se reutiliza solo con evidencia e identidad de entorno verificables; fallos, skips obligatorios, entradas incompletas y cambios de entorno no cuentan como PASS. Comandos con BD/red u otro estado externo solo se comparten si el ejecutor acredita ese estado. Dentro de una misma ronda se consolidan pruebas duplicadas cuando se demuestra la cobertura y el aislamiento requerido; los IDs recopilados por sí solos no prueban equivalencia de procesos.
5. La auditoría se registra por unidad y dominio con huella de alcance y reporte, vinculada a un despacho y resultado reales de un auditor independiente. La identidad/procedencia y la versión de las reglas forman parte del recibo. El cierre conserva los recibos actuales de unidades no afectadas y solicita solo los dominios de unidades invalidadas. Para evidencia antigua sin alcance suficiente se conserva el resultado histórico, pero se obtiene una evaluación del área cuyo alcance no puede acreditarse; no se fabrican eventos ni se solicita repetir auditorías de unidades demostrablemente intactas.
6. El cierre consolidado comprueba la línea base y todas las unidades activas, sus verificaciones y auditorías vigentes. Una enmienda nueva no reescribe ni revoca el sello histórico de otra. Una unidad en borrador no se confunde con aprobada. El cierre antiguo permanece disponible para proyectos heredados; la migración a unidades tiene una operación explícita y reversible.

## Aprobación y experiencia

7. El resumen de aprobación muestra el contenido completo pertinente, alcance, versión, impacto y digest. El consentimiento es el ya dado por el usuario para el incremento concreto; la interfaz visual es opcional. El registro debe vincular una interacción de usuario real al checkout, unidad y digest exacto, sin exigir repetir texto por formato y sin convertir mensajes del agente en aprobación. Los formatos largos se enlazan con hash completo y se comprueban con el hook real; Codex y la interfaz visual requieren una fuente real y verificable antes de activar su ruta.
8. El visor reúne árbol, objetivo, alcance, plan, tareas, versiones, pasadas y evidencias, obtenidos de datos reales. Estados desconocidos se muestran como tales. Las pantallas y estados se cotejan con el prototipo aprobado usando una ejecución y capturas reales; las diferencias se corrigen antes de declarar fidelidad. El botón visual de aprobación es opcional y comparte el mismo registro, no crea un segundo sello.

## Hooks, compatibilidad e instalación

9. El hook Codex recibe los eventos documentados y comprueba todos los destinos y el contenido que afecta reglas; las operaciones que no pueda reconstruir se rechazan con explicación, sin registrar éxito ficticio. Se prueba el contrato de entrada y salida con el host real; se documenta el límite de carreras entre precomprobación y escritura. La operación no debe debilitar reglas de proyectos existentes ni asumir cobertura de herramientas que el host no intercepta.
10. Linux y Windows utilizan rutas y codificación portables; se incluye UNC y el manifiesto de pruebas conserva LF. La instalación se planifica por archivos y hashes, preserva estado y personalizaciones, guarda respaldo y soporta recuperación si falla a mitad. El CLI, perfil y adaptador del proyecto se comprueban contra la misma versión; no se reinstalan directorios completos ni se modifica evidencia protegida.

## Orden y economía de validación

11. Primero congelar y revisar el diff existente y recuperar los componentes aislados; luego unidad/impacto, evidencia y verificación; después auditoría incremental y cierre; luego aprobación y visor; finalmente hooks, portabilidad e instalación. Un único responsable por archivo y compilaciones/BD en serie. Corregir en cada fase los hallazgos de revisión antes de conectar el componente siguiente.
12. Ejecutar una vez las pruebas focalizadas que ejercitan el cambio de cada contrato. La ronda integrada final cubre dos unidades disjuntas, dependencia compartida, cambios de tareas/código/regla/entorno/evidencia, falta de procedencia, rutas/alias, flujo heredado, visual y fallos/rollback de instalación. Registrar inicio, casos, skips y salidas. Un auditor independiente revisa solo el diff y las evidencias nuevas; no repite pruebas ya ejecutadas. La matriz Windows/Linux se reporta por entorno ejecutado, sin extrapolar.
13. Integrar y probar AIDD antes de actualizar perfiles y b1SycLink. Hacer commit y push con sus limitaciones reales; continuar b1SycLink por desarrollo pendiente y luego verificaciones. Las dudas que no bloqueen otras tareas se registran y se posponen para el final.

## Estado al cierre de esta ronda

`impact --changed --base` usa Git para filtrar tareas; `verify --tasks` y `verify --changed` ejecutan filas seleccionadas y registran evidencia parcial. El reuso solo admite filas Python con contrato offline explícito, entradas y entorno declarado verificables; el contrato no demuestra aislamiento. Una revisión real de Codex en un repositorio sintético registró dos dominios y una consulta posterior los reconoció vigentes. La revisión visual opcional registra el clic real por unidad, preservando los sellos anteriores. El visor enlaza la revisión activa. La evidencia histórica sin alcance acreditado permanece indeterminada. Los hooks Codex no son requisito por decisión del usuario. Las pruebas focalizadas integradas pasaron en Windows; no se afirma una ejecución Linux ni una comparación visual completa hasta tener evidencia de ambas.
