# Front 2 — Generator for `## Execution evidence` Table (AIDD R10 Optimization)

## 1. What Was Built
A stdlib-only Python tool and automated test suite located strictly inside `D:\Fuentes\AIDD\batch-staging\evidence-table\`:
- [`gen_execution_evidence.py`](file:///D:/Fuentes/AIDD/batch-staging/evidence-table/gen_execution_evidence.py): Parses the `Mapping ledger` (and `Open exceptions`) of `qa-audit.md` to identify codes marked done (`SCREEN-nn`, `SCREEN-nn-Fnn`, `API-nnn`, `-Fnn`, `T-nn`). Scans only spec-owned evidence paths (`evidence/`, `qa-evidence/`, `verify/`, `logs/`, root `*.png`/`*.log`). Performs strict literal word-boundary matching (`\b<CODE>\b`) across filenames and text execution files. Classifies valid R10 kinds (`screenshot`, `command-output`, `query-result`, `log`). Detects freshness against target code files (best-effort). Proposes the markdown table and reports coverage (total, mapped, unmapped with reasons, unmapped listed strictly as `not-verified` candidates, never auto-verified).
- [`test_gen_execution_evidence.py`](file:///D:/Fuentes/AIDD/batch-staging/evidence-table/test_gen_execution_evidence.py): Standard `unittest` suite creating and testing against an isolated synthetic spec folder in the staging directory (full mapping, unmapped code handling, freshness warnings, and dry-run file immutability).

## 7. Iteration 2 (2026-11-03): Verification Table `Covers` and Screenshot `by-number`

### A. Rules Added
In accordance with AIDD recorded data and strict auditability:
1. **Rule 1 (`literal`)**: Exact token match (`\b<CODE>\b`) in filename or content retained as first priority.
2. **Rule 2 (`by-number`)**: For `SCREEN-<NN>` codes, searches `evidence/**/s<NN>-*` and `SCREEN-<NN>*` by numeric value. Scores captured application views (`app.png`), loaded states, and standard desktop viewports over mockups and diff pairs.
3. **Rule 3 (`covers`)**: Cross-references `spec.md` `## Verification` table with `qa-audit.md` `### Closing gates`. A code covered by check `V-n` maps to `evidence/verify-V-n.txt` (or variant on disk) as Kind `command-output` **only if** `qa-audit.md` records a passing run (`Result: PASS`, never inferred from log text) **and** the file exists on disk.
4. **Audit Column (`Method`)**: Every proposed row explicitly identifies how it was mapped (`literal | covers | by-number`).
5. **Strict Candidate Policy**: All unmapped codes stay `not-verified` candidates with reasons; never auto-verified; zero writes to target repo or `qa-audit.md`.

   - In specs such as `P03`, `P04`, `S01`, `P06`, `P08`, `P09`, and `P11`, the author only listed `FR-` and `AC-` codes in the `Covers` column (e.g. `FR-001..FR-015`), leaving `API-nnn` unmentioned in `spec.md`'s Verification table.    - In specs `P02`, `S01`, `P08`, `P09`, and `P11`, screens only exist under `prototype/` (pre-implementation Figma/HTML prototypes). Under rule R10, prototype mockups are not executed evidence; they correctly remain unmapped candidates for human test verification.
