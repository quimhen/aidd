# Historical verification proof — isolated4b candidate

This note describes the owner-authorized isolated candidate. It is not an installation receipt or a declaration of independent audit PASS. Original and installed kernels remain unchanged by4b.

Dry-run skips both Round-identity and Docker identity probes in amendment and multi-spec routes. It executes no verification row and records no verification event. Ordinary read-only fingerprint collection remains possible; Git content hashing uses fixed argv with `--no-filters` so repository clean filters are not invoked by that hashing path.

Historical reuse requires an explicit `Reuse: hermetic`, nonempty Inputs and a complete offline Environment declaration, together with matching genuine prior policy, input algorithm, input proof and environment metadata. Planner and final consumer use the existing direct-Python offline validator. This is an owner-declared offline contract, not a sandbox. DB/docker/Node/unknown commands and Python `-m` do not gain reuse support.

Command/Expected identity, prior PASS, current lint, source artifact confinement/SHA1, live Inputs, current contract identity and transformed output binding remain required. The final consumer rechecks those conditions. A stale planned entry becomes an honest not-executed failure requiring replan; it never triggers an unplanned second execution of a heavy shared group. The separately approved4a full-header proof remains mandatory for a producer-truncated command; matching its first500 characters is insufficient.

Valid reused results preserve their existing revalidated contract metadata for a later safe carryover. Missing prior fields are not reconstructed from the current row. R10 evaluates every historical `reused` result against its unambiguous current Verification row; an unknown kind or a simultaneous `round_shared` flag does not bypass that policy. Genuine same-invocation actual sharing remains separate.

Coordinated amendment/round runs consume only the planner's explicitly validated historical entries or actual shared executions; local same-spec and immutable-store caches cannot override a planned RUN. `Regression: always` survives round collection and forces execution. Plain same-spec historical caches apply the same explicit contract and current input-algorithm guard.

Immutable-store keys, schema, version and producer remain unchanged. A stored object alone cannot establish its algorithm. Its consumer qualifies the unique matching result in the latest genuine source verify_run: current code/input algorithms, complete contract proof, actual live identity/Inputs, and the confined source artifact must all match the stored bytes/SHA. Missing, failed, unstable, ambiguous or stale latest-source proof means RUN, without falling back to an older PASS. Reused metadata comes from that validated source result; it is not backfilled into an old object.

The fingerprint semantic identifier is now `raw-sql-v3-nofilters-glob-v2`. Raw working-tree bytes, including CRLF/LF differences, are significant. Old, missing or unknown algorithm proofs must bootstrap through actual execution; no old event, artifact or receipt is rewritten or retagged. Some previously reusable rows therefore legitimately RUN once after controlled integration.

The authorized verification is the six targeted commands in security-boundary-spec.md, with the full actual transitive source/test identities and environment captured before/after. It does not schedule a broad123/48 replay or any database suite. Final integration, dependency-impact handling, owner version seals and runtime installation remain later controlled steps.
