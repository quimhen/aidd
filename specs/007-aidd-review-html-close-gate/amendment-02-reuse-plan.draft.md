## Behavioral contract

### First deliverable: one live observation, not a historical cache

The round must parse and validate every selected spec/row before starting any command. A participant is identified by the resolved spec directory and its unique row ID, never by the same row number alone. Duplicate spec aliases, duplicate row IDs, unsupported metadata or a participant discovered after launch fail preflight or run separately. `--full` always executes each row; initial implementation also falls back to independent execution for `--bail` or `Jobs > 1`, preserving existing semantics. It never invokes a producer command speculatively merely to calculate a key.

Round-scoped data contract (version `shared-round-v1`):

```
Participant = {spec_id: str, row_id: str, root: absolute canonical path,
               cwd: absolute canonical path, cmd: exact UTF-8 string,
               expected: exact parsed string, inputs: ordered list[str],
               input_fp: sha256 hex, policy_fp: sha256 hex,
               closure_fp: sha256 hex, shared_opt_in: true,
               runner_policy: "isolated-local-unit-v1"}
GroupKey = (root, cwd, cmd, expected, tuple(inputs), input_fp, closure_fp,
            runner_policy, effective_timeout, execution_context_id)
SharedResult = {schema: "shared-observation-v1", round_id: uuid4 hex,
                output_sha256: 64 hex, exit: int, expected: str,
                started: UTC timestamp, ended: UTC timestamp,
                participants: sorted list[(spec_id,row_id)],
                producer: (spec_id,row_id), object_rel: root-relative path}
```

`execution_context_id` exists only in round memory, is computed with a random per-round HMAC key from the actual subprocess environment and shell/interpreter/cwd/timeout, and is never written to log, event, receipt or error. The command inherits the exact snapshot used for grouping via explicit `Popen(env=...)`; secrets are never printed or retained. Different keys, absent context, undeclared Inputs, changed values, platform or runner policy => separate executions. Rows are eligible only after explicit owner-reviewed same-observation opt-in and a trusted runtime capability check confirms local-unit isolation with no host DB/network/socket/mutable external source. A declaration, mock provider, plain hash, or unknown command is not the capability check. The check establishes the safety of this *one* execution and does not attest equivalence with any past or later environment. Until a real platform-specific isolation check exists, production groups remain disabled; fake providers are available only to isolated tests and never registered by default.

`participants_digest` is SHA-256 of UTF-8 canonical JSON of the sorted unique `[spec_id,row_id]` pairs (`ensure_ascii=False`, separators `,` and `:`, no whitespace). Spec and row IDs must be nonempty and resolve to the preflight-selected in-root spec and row. The receipt records this digest and its own participant ID; neither the transient HMAC key nor an environment digest is persisted. Since the plan's isolation capability is not implemented or proven in the current runtime, synthetic capability stubs demonstrate planner behavior only: they do not authorize production grouping.

At preflight capture each participant's canonical verification-policy projection and the SHA-256 of the row's complete, demonstrable transitive closure of inputs, contracts and policy dependencies (including tool, runtime libraries, fixtures and config). Compute closure_fp from this row closure, not from the spec's aggregate Scope. The separately evaluated spec-level closure/verify gate retains its existing aggregate Scope and must not be treated as a row eligibility test. A demonstrably unrelated file change within that aggregate Scope does not invalidate the shared observation; it may independently make the overall spec verification stale under the aggregate gate, without authorizing spec PASS or forcing another execution of that row within the same shared observation. This is not historical reuse: a subsequent `verify` invocation executes the row again until a separately approved and verified historical-reuse phase exists. The projection contains the parsed row identity, command, expected, Inputs, opt-in, timeout and runner policy; the effective Scope and Generated declarations; the selected wave-to-task mapping, normalized Covers and the resolved row-to-FR/AC/task attribution, and declared relevant dependency closure. Both validators recompute the normalized Covers and attribution; a changed or unresolvable mapping invalidates attribution even if the command is unchanged. Encode it as versioned canonical JSON and hash it as policy_fp. Narrative prose, formatting, comments and unrelated task/requirement text are excluded only when the parser can prove they cannot change this projection. Unknown or ambiguous influence fails closed and prevents grouping. A relevant projection change before or during execution makes the observation stale; a proven irrelevant prose edit alone does not. `Generated` must not intersect a matched input; unknown overlap, unknown transitive dependencies, unreadable paths or ambiguous globs disable grouping. Recheck each snapshot immediately before launch and after completion. A changed relevant declaration, row input, dependency, policy or runner context while executing makes *all participants of that observation* stale; no partial PASS is emitted from that observation. A late joiner cannot attach to it. DB/network rows are excluded unless a separate provider proves snapshot identity and isolation; that work remains outside this first slice.

Storage contract: one UTF-8 stdout/stderr object containing the existing verify header and output is created atomically by the AIDD runner at `.aidd/evidence/shared/<round_id>/<output_sha256>.txt`, with strict hexadecimal components and no symlinks. The object is written once, never replaced by a differing object; failure to write/verify it makes every participant not verified. Each participant receives a new per-round receipt at `specs/<spec>/evidence/shared-receipts/<round_id>/<row_id>.json`; `round_id` is strict 32-character lowercase UUID hex, and the row ID is encoded to a deterministic path-safe component with collision rejection. The event's `evidence` points to this new in-spec relative path and its SHA-1 covers the receipt bytes. Never overwrite an existing `evidence/verify-<row>.txt`, an earlier receipt or an existing verify event. The receipt contains the schema, round_id, output_sha256, manifest reference/hash, participant spec/row identity and expected result. A later round creates a distinct path. Historical `evidence` pointers and hashes remain valid and are read using the legacy ordinary-evidence branch. Each `verify_run.results[]` retains its existing `n`, `evidence`, `sha1`, `exit`, `ok` and `expected` fields: `sha1` hashes the receipt bytes; adds `evidence_kind: "shared-observation-v1"`, `object_sha256`, `object_rel`, `round_id`, `producer_spec`, `producer_row` and `participants_digest`. It never claims a past `REUSED` hit. Legacy ordinary evidence remains byte-for-byte unchanged.

For every grouped observation persist a canonical immutable `shared-group-v1` manifest under the same permitted root. Its required `participants` array contains exactly one record per participant: `{"spec_id": string, "row_id": string, "policy_fp": lowercase 64-hex SHA-256, "closure_fp": lowercase 64-hex SHA-256}`. This is the mandatory mapping `(spec_id,row_id) -> (policy_fp,closure_fp)`, never a parallel list or group-level fingerprint. Sort records lexicographically by the UTF-8 bytes of `spec_id`, then `row_id`, with unique nonempty keys; derive `participants_digest` from these records' sorted `[spec_id,row_id]` pairs. Serialize all manifest fields with UTF-8 canonical JSON (`ensure_ascii=False`, `sort_keys=True`, separators `,` and `:`, no whitespace). Reject noncanonical order or encoding, malformed fingerprints, duplicate keys, missing or extra participant records, and any inconsistency with the frozen group or committed receipt. The manifest also contains round ID, producer, output SHA-256, exit, expected and timestamps; it contains neither environment secrets nor the ephemeral HMAC token. Its SHA-256 binds the manifest into every receipt and verify result, and `participants_digest` is recomputed from its actual participant list. A validator must prove that its receipt participant is in that list and the producer is a listed participant, not merely trust a digest copied into the receipt. Both validators must independently reconstruct the participant’s current canonical verification-policy projection and the current complete demonstrable row transitive closure, recompute their SHA-256 values using the same versioned algorithms, and compare both to that participant’s policy_fp and closure_fp in the manifest. Missing or unreadable inputs, unknown or incomplete closure, changed row/Scope/Generated/dependency, malformed projection or mismatch fails closed. A proven irrelevant prose edit or file outside the row closure does not alter these hashes; the independent aggregate spec gate remains unchanged. A transplanted receipt or mismatched/missing manifest is stale.

Participant journal schema `shared-participant-pending-v1` contains round_id, group_manifest_sha256, spec_id, row_id, receipt path and SHA-256, observation outcome and payload SHA-256; its unique idempotency key is the canonical tuple (round_id, group_manifest_sha256, spec_id, row_id). Replaying an identical key and payload is a no-op; the same key with any different payload is a hard conflict. The ordinary aggregate `verify_run` remains the per-spec source of verdict and must include the expected row set and their evidence references; pending journal records alone never mean PASS. A row is eligible for aggregation only when its committed marker binds its exact pending record and receipt. Missing, incomplete, duplicated or conflicting row records make aggregate verification non-PASS. Recovery reconstructs or completes the aggregate idempotently from committed records and ordinary row results without spawning the completed shared observation; it must not invent a missing row or overwrite legacy events.

Durability contract: before advancing a publication phase, write a new temporary file, flush and fsync the file, atomically rename into its exclusive final path, and fsync its containing directory; journal appends must be flushed and fsynced before committing. Publish the marker by the same sequence only after durable prerequisites and snapshot revalidation. The adapter must positively prove these operations and required exclusive-create/rename semantics on the actual filesystem and platform; unsupported, failed or uncertain durability means fail closed and no shared PASS. No platform-independent fsync guarantee is assumed.

Publish using a two-phase group protocol: atomically write and verify the immutable output, group manifest and each participant receipt to new paths; after all are durable, append each participant event in pending state; only after every event is durably recorded and all snapshots revalidated, write one final atomic `committed` marker bound to the group-manifest hash, every receipt hash and every pending-event identity. Never replace an existing different object or marker. Every validator requires this marker, validates the manifest, proves its receipt is among the committed hashes, and rejects missing/corrupt pieces. If any write, validation, participant snapshot or event recording fails, or the process crashes before commit, no participant can pass; an incomplete group remains recoverable/garbage-collectable without deleting evidence used by another committed group. After commit, recovery may rebuild derived indexes from committed events without re-executing the subprocess, only while all proofs still verify. Concurrent rounds use distinct IDs and exclusive creation, and cannot attach participants after preflight.

Both `aidd_rules._run_problems` and `aidd_status._json_pass_evidence_problem` must explicitly distinguish receipt from ordinary evidence. For a receipt, resolve only the allowed shared root, reject absolute paths, traversal, symlinks and mismatched participant/round IDs, verify receipt SHA-1 and object SHA-256, then run existing exit/expected/zero-test checks on the *object*, not on the receipt. Missing/corrupt object, receipt, unexpected schema, mismatched participant or unsafe path is stale/fail-closed in both close and JSON. For ordinary evidence, retain the existing in-spec path and SHA-1 rules. Archive/restore or cleanup may remove an object only after all dependent receipts expire; deletion must immediately invalidate all consumers. Evidence references are not proof of future environment equivalence.

1. **One actual run vs historical revalidation:** plan a round before spawning subprocesses. A single run may cover multiple explicitly opted-in rows only when it is actually one observation at one time and all criteria below pass. It is not called `REUSED` and cannot be used as a historical hit in later rounds. Preservation of a receipt or object does not authorize skipping a subsequent verification: without separately approved and proven historical reuse, each later invocation executes a new observation. Explain this distinction in CLI output and JSON. `--full` bypasses grouping entirely. No historical environment identity provider is required to establish that a single observed subprocess has a single contemporaneous environment; current-round isolation and context checks above remain mandatory.
2. Initial candidate identity is the exact command representation (do not normalize shell text into semantic equivalence), canonical project root and working directory, Expected, ordered explicit Inputs, row-closure fingerprint and exact provider/runner policy. Context equality must be verified from effective subprocess inputs, not claimed only by a spec author. Differences in cwd, env or input declarations prevent grouping. Include actual consumer spec IDs and verification-row IDs before execution; do not admit late joiners.
3. Shared eligibility is scoped to the verified transitive closure of each row, not the spec aggregate Scope; the aggregate spec-level close gate remains separate and unchanged. `Inputs` are explicit root-relative safe patterns and must include command, tool, test, fixtures, project configuration and **transitive runtime dependencies**. An enumerator that cannot prove closure returns unknown and disables grouping; a graph heuristic alone is not proof. Resolve globs consistently, reject traversal/symlink escapes, capture stable bytes before/after and treat unreadable/missing/ambiguous inputs as unsafe. Never derive include/exclude rules from `Generated` without verifying whether each path is an output or input.
4. Identify effective environment through an independently verified provider and record its version and capability proof; the verifier determines profile eligibility, not the model or an untrusted user-authored `hermetic` flag. Compare effective executable/interpreter and relevant settings, platform and runtime; no secret values, secret hashes, credentials or environment dumps in logs. Use an ephemeral in-memory keyed equality token for sensitive values within a round and discard it afterwards; unavailable context => no group. Tests inject deterministic fake providers only; fake proof is not production trust.
5. Initial implementation may group only local unit-test rows in a runner with verified isolation and closed inputs. DB, network, mutable services, time-dependent effects, external datasets and side-effecting commands are ineligible absent a separately reviewed provider proving a matching immutable snapshot and isolation. An unavailable OS sandbox or partially verified provider must refuse eligibility rather than silently run unprotected as a shared result. This conservative requirement can result in zero saved runs until the provider is proven; report it honestly.
6. On grouped execution, write one content-addressed immutable evidence object atomically; each consumer receives a reference, not a repeated copy. Per-spec V-IDs and result metadata remain independent. Consumers get PASS only after exit/expected/nonzero-test validation, evidence digest and all pre/post snapshots are checked, and command completed normally. A corrupt, missing or replaced object, timeout, changed Inputs or changed context yields not-verified/stale, never inherited green. Preserve historical evidence and don't delete another spec's evidence. Audit compatibility with existing `verification_gaps` and `verify_output_problem` before changing storage.
7. Cross-round reuse, DB snapshots and audit carry-over are **future gated work**, not implied by FR-214/215. Any future trusted provider must attest runner and effective external state through an authenticated source; a JSON file writable by the same agent, a cryptographic digest alone, a timestamp or a declared label is not an attestation. A changed fingerprint cannot migrate a legacy result by inventing a prior signature.
8. Preserve the current command contract and default behavior when no provider is verified. Offer a read-only explanation for every candidate: reused/shared/executed/stale, exact mismatch category, source evidence ID and measured duration; do not expose secret values or low-entropy secret hashes. `--full` and consumer-specific commands remain available. Measure actual subprocess counts, runtime and input changes rather than claiming projected token savings.

## Release / dependency boundaries

Current host does not expose a demonstrated authenticated audit-unit event or trusted external-environment provider; do not implement their apparent support with synthetic tests. Carry-over of audit evidence must be separately approved under 006/008 once the producer and event authentication exist. Any unit/screen dependency manifests from 008 must be consumed only after their schema and traversal are approved; fallback is always conservative.

## Validation and audit

Focused synthetic tests exercise one actual subprocess with two specs, different cwd/env/inputs/expected, late participants, input mutation during process, timeout, nonzero result, zero tests, corrupted evidence, no provider, forged manifest, external/DB/network refusal and full mode. Compare subprocess counts and evidence references. A separate proof-of-capability smoke for any real provider is mandatory on each supported OS; unavailable platform = disabled, not pass. One independent auditor checks attribution, stale detection and security without rerunning shared tests. Final `aidd verify` and closing audit retain the project's independent gate.
