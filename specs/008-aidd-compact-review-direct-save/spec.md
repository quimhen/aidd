## Executive summary

- Objective: the owner approves a spec with ONE short, tabbed page (confirm what the AI already generated), the page saves `review.md` into the spec folder by itself, and the agent then asks a single tagged confirmation: no file moves, no typed line.
- Scope: in = compact page (8 tabs including `Verificación`, one check per code), executive summary in `spec.md`, `review.md` one line per code, File System Access save with download fallback (folder validated by spec id and tasks hash), `aidd review --wait`, `--full` keeps today's long page, owner-facing messages and docs; ONE final button that reads `Guardar progreso` until everything is checked and lists what is missing (FR-310), Verification rows checked by hand (FR-311), checks of unchanged items carried over when the page is regenerated (FR-312); the agent reads ONLY the approval state (one status line from `--check`/`--wait`, `--comments` only when comments > 0), never the full `review.md`/`review.html`; the review mode is the owner's choice (FR-313): ONE tagged question with `Revisar en HTML visual` (only then the page is generated) or `Aprobar con resumen` (the mechanical `aidd review --summary` text shown inside the question, the click is the approval). Out = any other change to consent, approval hash, R6 gate, verify/close gate.
- Cost: 78 min / 880k tokens (8 tasks, 3 waves; wave 1 runs 4 builders in parallel; wave 3 is audit and executed verification).
- Risks: direct save only works in Chrome/Edge (Firefox/Safari download `review.md`); a code missed by the extractor would not be reviewed (mitigated by accepting the code shapes real specs use, an independent completeness count and per-tab warnings that name the skipped codes); two review.md grammars coexist (compact `codes-v2`, `--full` `headings-v1`).
- Open decisions: O-1..O-14 at the end of this file (quotes for the owner to confirm).

| FR-301 | Reviewable model by CODE. `aidd_review.extract_items` turns the five sources into ordered tabs and unique codes: `SUMMARY` (summary tab); `Q1..Qn` (checklist rows first, then Optional Align rows, positional unless the Question cell starts with an explicit `Qn`) followed, in the same `Preguntas` tab, by `D<n>` for every row of every `## Decisions...` table (the owner-confirmed answers with their Source quote); `FR-nn`, `AC-nn`, `SCREEN-nn` / `COMP-nn` / `CTL-nn`, `API-nn`, `T-n`, `V-n` (rows of the spec.md `## Verification` table, FR-311). **Code shapes are the ones real specs use**: 1 to 4 digits (`FR`, `AC`, `T`) or 1 to 5 digits (`API`, `COMP`, `CTL`, `SCREEN`) plus an optional one-letter suffix, joined or hyphenated (`FR-004b`, `AC-007b`, `AC-01`, `AC-01a`, `AC-01-b`, `AC-01-n`, `FR-004-x`, `T-1`, `D24b`, `V-5`); digits are ASCII only and the whole token must match (Python `re.ASCII` + `fullmatch`, so `FR-٣` and `FR-1` followed by a newline are not codes). The code is the FIRST TOKEN of the first cell (backticks and bold stripped, trailing comma dropped), so `API-<nnn> fe_param` is the code `API-027` and the rest becomes item text. Rows are taken from EVERY table of the source (never only the first table under a heading); the first occurrence of a code wins, repeats (navigation maps such as the Origin/Action flow table, traceability tables) are skipped and reported in ONE counted line, so codes are unique. Template placeholders (the WHOLE token is a placeholder: `FR-nnn`, `SCREEN-XX`, `SCREEN-XX-Fnn`; `AC-01-n` and `FR-004-x` are real codes, not placeholders) and field rows (`SCREEN-nn-Fnn`, `COMP-nn-Fnn`) are never items and never counted as skipped. **Completeness check**, independent of the extractor: per source it counts the distinct coded first cells (generic `^(FR\|AC\|API\|T\|SCREEN\|COMP\|CTL\|V)-\S+`, minus placeholders and field rows), compares with the extracted count, and on any difference shows a per-tab warning that NAMES the skipped codes (first 8). A row in an Acceptance cases or Decisions table that has no code at all (for example F23 `Mixed payment sale`, `C1, C2, C3`) is not invented a synthetic code: the same per-tab warning says "N rows without a code are not reviewable: <first titles>", and a tab with 0 items but a non-empty source keeps that warning on the Resumen tab. Item text is one short line (cells cut at 240 chars with `...`, markdown emphasis stripped). Tabs with 0 items are not emitted (a backend-only spec has no `Pantallas` tab). Cap: `MAX_ITEMS = 2000` (real specs reach about 560 items; the compact page stays small). Above it the compact review is refused fail-closed with the reason `too many items (N > 2000): split the spec or run aidd review <spec> --full`. That reason is NOT `source too large`: it blocks BOTH approval routes (no answer-only route), `--check` and `--wait` exit 3, and it applies only while the current page is not a `--full` page (the `--full` page has no item cap). The item-cap check runs BEFORE the no-`review.html` shortcut of FR-304 and its reason wins: a refused compact page leaves no `review.html`, so with the opposite order the spec would fall into `no review.html` and an answer-only route could reopen. The 400 000-char source cap of 007 and its answer-only route are unchanged. Never raises. | — |

| FR-304 | `review.md` grammar `codes-v2`. Front matter `spec`, `tasks_hash`, `sources_digest`, `format: codes-v2`, `approved`, `generated`, `reviewed`; body one line per code: `- [x] FR-301` / `- [ ] FR-301`, optionally ending in ` @<d8>` (the item digest of FR-312 for the page it was saved from: `- [x] FR-301 @1a2b3c4d`; a line without it is valid and simply carries nothing over), optionally followed by `> comment` lines (at most 5 lines and 500 chars per code); the code on a line is any code of FR-301 (so `- [x] FR-004b` and `- [x] D24b` are valid). **Formats and `legacy`, defined once:** the two grammars are `codes-v2` (compact page) and `headings-v1` (the 007 heading grammar, still valid for `--full`). `parse_review` returns `format`: the `format:` front-matter value, and `headings-v1` when the line is missing; an unknown value is invalid. ## Risks and residuals

- Direct save is Chromium-only (Chrome/Edge 86+, also on `file://`); Firefox and Safari keep the download path, so "no manual step" is only fully met on Chrome/Edge. The page and the docs say so.
- `file://` pages share an opaque origin in Chromium: the remembered folder handle may be lost; the cost is one extra pick (the picker reopens at the last location).
- The written executive summary is not verified content; the generated counts and totals are shown beside it so the numbers are mechanical.
- Real specs mix code shapes (`FR-004b`, `AC-01a`, `AC-01-b`, `T-1`, `API-<nnn> fe_param`) and some have no code at all in a table (F23 acceptance cases): the accepted shapes, the independent completeness count and the named per-tab warnings keep a skipped row visible; a shape nobody has written yet is reported, never silently dropped.
- Positional `Qn` codes shift when a row is inserted; `spec.md` is in the digest, so the old `review.md` is stale and cannot mix comments across questions; the per-item digest of FR-312 includes the row text, so a shifted `Qn` returns to pending instead of carrying another question's check.
- Carry-over (FR-312) re-presents unchanged items as already checked: the owner sees `Arrastrados N de M` and the pending list, still presses the final button, and the consent is still a new tagged click newer than the re-saved `review.md`; a carried check never approves by itself.
- FR-313 lets the owner approve on a ~25-line mechanical summary without seeing every item: it is his explicit, recorded choice (exact label, tagged, hook-recorded), the agent can never pick it, and the summary numbers are mechanical.
- A forged `review.md` is possible for any local process (as in 007); the trust root is the tagged click recorded by the hook after `review.md`. `--wait` must never approve.
